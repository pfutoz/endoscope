1. 開発計画の背景と基本方針

内視鏡予約管理システム（Modernized Edition）は、予約マトリクス、月間カレンダー（日別メモ連携・出勤例外完全連動）、診療科別初期値制御、空き枠検索アルゴリズムの是正等を経て、予約・枠管理の基本機能群をすべて完備し、安定稼働フェーズへ移行しました。
本計画書は、さらなる「内視鏡室の現場DX」「医療事故ゼロ化」「システム保全（BCP）」「患者・窓口サービス向上」に向けた次期開発項目とアーキテクチャ方針を整理したものです。

🎯 中核方針（コア・コンセプト）
  • 「予約予定」から「当日現場動線」への拡張: 確定した予約データをモダリティ機器や内視鏡室モニターへ直接繋ぎ、現場スタッフの手作業・二重入力を徹底排除。
  • 強固な医療安全とセーフティネット: 抗血栓薬の休薬確認や感染症対策をシステム側でアシストし、万が一の誤操作（誤削除・誤移動）に対するUndo復元機能を担保。
  • 責務分離（SoC）とBCPの確立: DBバックアップ・リストアなどの基盤保全は、Web予約システムから切り離して独立運用し、単一障害点（SPOF）を排除。

3. 計画② 院内総合データベース・リストアシステム（独立運用）

🛡️ 全DB一括バックアップ連携 ＆ 3段階リストアシステム 独立運用ツール / PowerShell GUI / BCP対策
運用設計フェーズ

日次自動バックアップスクリプトにより C:\dbbackup\YYYYMMDD に保存されている 00_globals.sql および各DBの .dump（-Fc カスタム形式）を安全かつ迅速に復元するため、Web予約システム本体から完全に切り離された独立総合リストアツール を構築します。

💡 なぜWeb予約システムと切り離すのか？（アーキテクチャ上の必然性）
DB破損やApache障害などの緊急時、Webシステム内に復元機能があると「管理画面が開けずリストアを実行できない」というデッドロックに陥ります。他システム（電子カルテ関連等）も含めた共通インフラとして独立ツール化することが医療情報システムのベストプラクティスです。
⚙️ 総合リストアシステムの必須機能要件
機能項目 実装仕様・アプローチ 現場効果・安全設計
1. セッション強制切断
(セッションKick)		 リストア対象DBに対し、実行前に pg_terminate_backend(pid) を発行し、稼働中の全クライアント接続を切断。 「他ユーザーがアクセス中」によるリストア処理のロック・失敗を100%回避。
2. 3段階の復旧モード ・全損復旧: 00_globals.sql ➔ 全DB順次展開
・単一DB復元: 対象DBのみ選択して上書き復元
・テーブル単位救済: pg_restore -t [テーブル名] 		サーバー交換時の全復旧だけでなく、「予約テーブルだけ誤って消した」等の局所インシデントにも最小限の巻き戻しで対応可能。
3. 検証用DBへの
事前テストリストア		 本番DBへ直ちに上書きせず、一時DB（例: restore_test_db）へリストアしてデータ件数・最新日付を確認するモード。 リストア日付の選択ミスによる「正常な本番データを過去データで上書きしてしまう事故」を未然に防止。
💻 コア・コマンドライン仕様（PowerShell / pg_restore）
# 1. 接続セッション強制切断 & "$pgBinPath\psql.exe" -U $dbUser -d postgres -c "SELECT pg_terminate_backend(pid) FROM pg_stat_activity WHERE datname = '$targetDb' AND pid <> pg_backend_pid();" # 2. 単一DBクリーンリストア (-Fc 形式) & "$pgBinPath\pg_restore.exe" -U $dbUser -d $targetDb --clean --if-exists -v "$dumpFilePath" # 3. 特定テーブルのみのピンポイント救済（例: t_schedule のみ復元） & "$pgBinPath\pg_restore.exe" -U $dbUser -d $targetDb -t t_schedule "$dumpFilePath"

⚠️ なぜ「コード（waku_id）参照優先」が医療システムで危険なのか？
例えば、マスタ上で waku_id = 12（旧：GIF 9:00）の行を管理者が CF 14:00 に書き換えてしまった場合、waku_id で紐付けていると、すでに患者様へ「朝9時の胃カメラ」と案内して予約票を渡した未来の予約データが、画面上で全て自動的に「14時の大腸カメラ」に化けてしまいます。現場スタッフは「元々何時の何の予約だったか」を知る術を失い、ユーザー側での復旧も不可能になります。

比較観点 ❌ コード（waku_id）優先参照方式（危険） ⭕ 枠名称文字列（scheduled_time）保持方式（採用）
マスタ修正時の挙動 マスタの枠名や時間を変えると、既存予約の表示枠が裏で勝手に新しい枠名へすり替わる（サイレント改変）。 マスタと文字列が一致しなくなった予約は、すり替わらずに「🚨 迷子（旧枠名）」として警告表示される。
当時の予約証跡の保全 予約テーブルにコードしか無い（またはコードを優先する）と、患者と約束した元の枠名が完全に消失する。 予約レコード自身が scheduled_time = 'GIF9:00' という予約確定時の事実（スナップショット）を永久保持する。
ユーザー側でのリカバリ どの予約が巻き添えで変わったか判別できず、現場スタッフの手で修正することが一切できない。 カレンダーや一覧で 🚨 迷子 (GIF9:00) と明示されるため、スタッフが予約編集（✏️）から安全に正しい枠へ手動振り替え可能。

💬 現場のリアルなCF予約フロー：
大腸内視鏡（CF）の予約は、「〇月〇日に受けたい」という日付先行ではなく、「〇〇先生に検査してほしい ➔ だいたいこのあたりの時期で空いている日はないか？」という【医師指名 × 時期俯瞰】の順序で決まります。
そして枠が埋まりつつある「枠限界付近」において、スタッフは「その日の各医師の限界数（定員）」と「現在入っている検査数（どの物理枠に誰先生が入っているか）」の2つを見比べて差し引き計算し、本当にまだ入れられるかを判断しています。
課題の論点 現行Webシステム（3枠・複数突っ込み型）の弱点 紙ベースの台帳が優れていた理由 ＆ 次期システムが目指す姿
① 1枠に複数件入るため
「物理的な空き」が見えない		 CF枠が3列しかないため、常時1つのマスに2〜3人の患者タイルが縦に重なって入る。結果、「1人入っているマス」が満杯なのかまだ入るのか、今日全体で何件埋まっているのかが直感的に分からない。 紙の台帳は原則「1物理枠（1行）＝1患者」（例：8枠）。
➔ 2027/2/1からCF枠を8枠に拡大することで、通常運用時は「原則1マス＝1件」の明快な物理構造を取り戻す（※枠名自体は医師名と連想させない中立な名称とする。また、急患やイレギュラー検査に対処できるよう、システム上は現状と同じく1つの枠に複数の予約を重ねて入れられる仕様を制限せず維持する）。
② 8枠に増やすと横幅が伸び、
「医師限界数」と「物理枠」を
同時に見比べられない		 単純にCF枠を3列➔8列（全体で20列超）に増やすと、month_matrix_v2.php の横スクロールが膨大になる。右側のCF枠を見ると左端の「医師の限界数（例：義 🟢2/3）」が遠く離れ、視線を左右に往復させて差し引き判断することが困難になる。 紙の台帳は1枚の紙面上に「その日の医師の限界数（参考枠）」と「8つの物理枠の埋まり具合」が一覧で収まっていた。
➔ 情報を間引いてでも全枠が1画面に収まる「コンパクト全表示モード」や「差し引きアシスト表示」が不可欠。
③ 枠限界付近での
「誰先生なら可能か」の判別		 物理枠が8枠あっても、その日の出勤医のCF限界数合計が「5件（例：義智3＋慶太郎2）」の日には、5件埋まった時点で残り3枠は実質予約不可となる。また「4件埋まった時点で、最後の1枠は誰先生の枠か」を瞬時に読み取る必要がある。 「左端の医師別限界数・残数」と「右側の物理枠に入っている医師アイコン」の対比を極限まで近づけ、さらにシステム側で残枠のある医師や定員到達を視覚的にガイドすることで、紙を超える判断速度を実現する。
⚙️ 2. 基本時間枠マスタ（m2_waku）期間（世代）対応の設計仕様と影響範囲

まずは時間枠マスタ（slot_master_maintenance.php?tab=waku&dept=GASTRO 等）のみを期間対応（世代管理）とし、「期間対応一括変更」によって特定日を境に枠構成・枠名称が丸ごと切り替わる仕組みを構築します。

  • 世代（期間）定義の例:
    • 現行世代: 1900-01-01 〜 2027-01-31（従来の枠構成・名称）
    • 新世代: 2027-02-01 〜 9999-12-31（画面表記 2027.2.1 〜 9999.9.9：CF 8枠化・新名称）
  • ユーザー体験（自動切替）: カレンダーや予約モーダルで 2027-01-31 以前の日付を開けば現行枠が表示され、2027-02-01 以降の日付を選択した瞬間にたちまち新名称の8枠へ自動切替されます。予約表示・マトリクス・日別印刷もすべて対象日の世代に従います。
  • DB変更（1テーブルのみ）: m2_waku に valid_from DATE NOT NULL DEFAULT '1900-01-01' と valid_to DATE NOT NULL DEFAULT '9999-12-31' を追加。行単位のバラバラな期間設定による設定ミスを防ぐため、診療科ごとの「期間セット（世代）一括変更・新世代コピー生成」方式とします。
  • 【重要要件】イレギュラー対応のための「同一枠への複数予約許容」の維持: 「1枠1予約」は8枠化によって通常時の見通しを良くするための運用上の原則であり、システム上で1枠1件にロック（制限）することはせず、現状と同じく同一枠へ複数の予約を登録・移動できる仕様をそのまま残すことで、急患・追加・イレギュラー検査に柔軟に対処できるようにします（コンパクトモード時でも1マスに複数件入った場合は縦に2段スタック表示または件数バッジ等で視認可能にします）。
