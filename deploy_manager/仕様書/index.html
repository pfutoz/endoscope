1 システム概要と開発背景

「院内システム総合デプロイマネージャー」は、医療法人小野会における院内Webアプリケーション群（内視鏡システム、手術台帳、カルテビューア、ヒヤリハット、予定管理等）の開発端末（ローカルApache環境）と本番サーバー（192.168.1.16）間におけるソースコードの**同期・配布（デプロイ）・世代バックアップ・ロールバック（復元）**を極めて安全かつ迅速に行うために開発された専門管理システムです。

主要な目的と提供機能

  • 全自動の事前バックアップ担保: 本番サーバーへのファイル上書き前に、上書き対象となる既存ファイルを抽出してタイムスタンプ付きZIPアーカイブを自動生成。人的ミスによるコード消失や不具合を100%防止。
  • 精密な差分検知: ローカルと本番の全ファイルを高速に再帰スキャンし、サイズおよび更新日時の差（2秒しきい値）から「更新 (MODIFIED)」「新規 (NEW)」「一致 (SAME)」を自動分類。
  • ワンクリック・ロールバック: デプロイ後に予期せぬ不具合が発生した場合、履歴一覧から対象時点を選択して「復元」ボタンを押すだけで、本番環境を過去の確定状態へ即時復旧。
  • ゼロ構成・標準機能駆動: Node.jsの標準モジュールおよびWindows標準のPowerShell / VBScriptのみで構築。外部ライブラリ（npm install等）への依存を一切排除し、PC交換時やOS再インストール時も即座に復元可能な堅牢性を実現。
✅ 安定稼働の実績
複数回にわたる院内デプロイ検証を経て、ファイルの取りこぼし、パーミッションエラー、プロセスハングアップが皆無であり、極めて安定した稼働状態が実証されています。

3 技術的課題と設計決定（核心原理）

3.1 なぜ Apache (PHP) 単体では本番配布が不可能なのか？

開発初期段階では、ローカル開発環境のApache上で動作する api.php を通じて本番サーバー（\\192.168.1.16\htdocs）へ直接ファイルをコピーする設計が検討されました。しかし、Windows環境特有の厳格なセキュリティモデルに起因する致命的な制約が判明しました。

⚠️ Windowsサービス (NT AUTHORITY\SYSTEM) のSMB遮断仕様
ローカルのApache HTTP Serverは、Windowsサービスとして NT AUTHORITY\SYSTEM（LocalSystemアカウント） で動作しています。
Windowsのセキュリティ仕様上、SYSTEMアカウントはネットワーク越しのSMB共有フォルダ（ネットワークドライブ T: や UNCパス \\192.168.1.16\...）に対して認証トークンを送信できず、「アクセス拒否（Access Denied）」となります（Null Sessionの禁止規則）。

この制約により、ブラウザから api.php を呼び出して本番サーバーへファイルを転送・比較しようとすると、本番フォルダが存在しないと判定されたり、ファイル書き込みがすべてエラーとなってしまいます。

3.2 一般ユーザー権限常駐 Node.js デーモンによるブレークスルー

この問題を根本解決するため、「Windowsにログインしている一般ユーザー（Owner）の権限で動作するバックグラウンド常駐サーバー（Node.js）」をポート 5050 に配置するアーキテクチャが採用されました。

  • ユーザー資格情報の継承: 一般ユーザープロセスとして起動されるため、Windowsエクスプローラーで保存された T: ドライブのネットワーク資格情報（本番サーバーへの認証セッション）がそのまま有効になります。
  • 完全非同期・安全なファイルI/O: Node.jsのファイルシステムAPIおよび子プロセス実行（child_process）により、本番サーバーとの大容量ファイル通信、ZIP圧縮・解凍、タイムスタンプ制御を確実に行うことができます。
  • ダブルアクセス経路の冗長性: UIおよびAPIは、http://localhost:5050/（Node.js直通）だけでなく、Apacheの http://localhost/deploy_manager/ からもCORS（Cross-Origin Resource Sharing）ヘッダーを介して相互にシームレスに連携できます。

5 詳細動作原理とアルゴリズム

5.1 差分検知（スキャン）原理

差分検知は、ローカルディレクトリ（c:\Apache24\htdocs\<system>\）を再帰的に走査（scanDirectoryFiles）し、本番環境の対応ファイルと照合することで行われます。

除外フィルタリング規則

開発環境に特有の管理ファイルや一時ファイルが誤って本番に配布されないよう、以下の強力な除外フィルターが適用されます：

  • 除外ディレクトリ: .git, .agents, .gemini, node_modules, vendor, scratch, bak, ip_bak, gitshare, deploy_manager
  • 除外ファイルパターン: *.bak, *.tmp, *.log, test_*.js, scratch_*.js, Thumbs.db, desktop.ini

判定ロジックと2秒しきい値の理由

// 差分判定ロジック (server.js lines 201-216)
const isDiff = (lf.size !== pStat.size) || (Math.abs(lf.mtime - pStat.mtimeMs) > 2000);

if (isDiff) {
    status = 'MODIFIED'; // 既存ファイルに変更あり
} else {
    status = 'SAME';     // 完全一致
}
// 本番にファイルが存在しない場合: status = 'NEW' (新規追加)
💡 2秒しきい値（2000ms）を採用している技術的理由
WindowsのFAT/SMBファイルシステムやNTFS間のファイルコピーでは、OSの仕様によりタイムスタンプの精度に最大2秒の分解能差異（2-second granularity）が生じる場合があります。そのため、1秒未満の微細な時間ズレで「更新」と誤誤認される現象を防ぐため、業界標準の2秒しきい値を設けています。

5.2 事前ZIPバックアップ機構（フェイルセーフ設計）

本システムの最も重要な安全機能です。ユーザーがデプロイを実行した際、本番ファイルを1つでも上書きする「直前」に以下のステップが厳格に実行されます：

  1. 配布対象として選択されたファイルのうち、本番サーバー側に既に存在しているファイルのみを特定。
  2. 一時ステージングディレクトリ（c:\deploy_backups\<system>\_staging_YYYYMMDD_HHMMSS\）に対象ファイルを相対パス構造を保ったまま一時退避。
  3. PowerShell標準の Compress-Archive コマンドを実行し、日時付きZIP（例: endoscope_backup_20261002_123045.zip）を生成。
  4. ZIPファイルが正常に生成されたことを確認（fs.existsSync）した後にのみ、一時ステージングを安全消去し、次の配布処理へ進む。
  5. 【強制中断機構】: もしZIPバックアップの生成に失敗した場合、デプロイ処理は即座に中止され、本番ファイルには一切触れません（ゼロ変更の保証）。

5.3 安全配布（コピー）処理

事前バックアップの成功後、ローカルから本番サーバーへのファイルコピーが行われます。

  • 階層ディレクトリの自動生成: fs.mkdirSync(path.dirname(dest), { recursive: true }) により、新規追加されたサブフォルダも本番側に自動作成されます。
  • タイムスタンプ完全同期（utimesSync）: ファイルコピー後、ローカルファイルの更新日時（mtime）およびアクセス日時（atime）を本番ファイルに適用します（fs.utimesSync(dest, srcStat.atime, srcStat.mtime)）。これにより、デプロイ完了後の次回スキャン時に即座に「✓ 一致 (SAME)」と判定され、再配布の重複を防ぎます。

5.4 ワンクリック・ロールバック機構

本番環境に不具合が発覚した場合、画面の「🕒 過去バックアップ ＆ ロールバック」タブから対象のZIPを選択して復元を実行します。 

// server.js lines 426-429
const psCmd = `Expand-Archive -Path '${zipPath}' -DestinationPath '${prodDir}' -Force`;
execSync(`powershell -NoProfile -Command "${psCmd}"`);

PowerShellの Expand-Archive -Force オプションにより、該当のZIPに格納されている確定状態のファイル群が本番サーバー（T:\<system>\）へ一括で直接上書き展開され、数秒で元の安全な状態に巻き戻されます。

6 自動常駐・プロセス管理機構

日常業務において、開発者が意識してサーバーを起動する手間をなくすため、Windowsの標準機能のみを活用した洗練された自動常駐メカニズムが組み込まれています。

【Windows サインイン時】 │ ├─ スタートアップフォルダ: %APPDATA%\Microsoft\Windows\Start Menu\Programs\Startup\ │ └─ Onokai_Deploy_Manager_Daemon.vbs (自動実行) │ │ │ ├─ WScript.Shell.Run (ウィンドウ表示スタイル = 0: 完全非表示) │ ▼ │ node.exe "c:\Apache24\htdocs\deploy_manager\server.js" │ │ │ └─ ポート 5050 でバックグラウンド待機 (メモリ消費約 25MB の軽量常駐) │ ▼ 【ユーザーがブラウザで開く】 └─ http://localhost:5050/ (即座に操作可能・黒いコマンドプロンプト画面は一切出ない)

常駐管理の要点

  • 黒い画面（コンソール）の完全抑止: startup_launcher.vbs 内で WshShell.Run cmd, 0, False を指定することにより、コマンドプロンプトのウィンドウを一切表示させずに完全なバックグラウンドサービスとして実行します。
  • 多重起動の安全制御: start_server.js は起動前に netstat -ano -p tcp をチェックし、ポート5050が既に待機中（LISTENING）の場合は新規起動をスキップしてブラウザのみを開くため、多重起動によるポート衝突が起きません。

8 セキュリティ・整合性設計

パストラバーサル（ディレクトリ遡り）の防止

システム名パラメータには厳格な正規表現バリデーション（/^[a-zA-Z0-9_\-]+$/）を適用。../ や ..\ を含んだ不正なリクエストを完全に遮断し、意図しないディレクトリの走査や書き換えを防止しています。

ロールバックファイル名のサニタイズ

path.basename(body.zipFilename || '') を通すことで、バックアップファイル指定におけるディレクトリ指定を強制的にファイル名単体に丸め込み、バックアップディレクトリ外のファイルを解凍・実行させる攻撃を無力化しています。

リッスンアドレスのローカルホスト限定

支援サーバー（server.js）は、外部ネットワークからの不正アクセスを防ぐため、明示的に 127.0.0.1（localhost）のみにバインドしてリッスンしています（外部からのポート5050直接接続は不可）。

9 環境自己診断 ＆ トラブルシューティング

万が一のPC障害、Windows Update後のトラブル、端末の移行時に備え、UI画面上およびコマンドラインの両方で一発診断が可能な機構が備わっています。

PC交換・OS再インストール時の復旧手順（完全3ステップ）

  1. Node.js (LTS版) のインストール: 公式サイト（nodejs.org）から推奨版インストーラー（.msi）をダウンロードし、標準設定のままインストール。
  2. 本番サーバーの「T:ドライブ」割り当て: エクスプローラーで \\192.168.1.16\c$\Apache24\htdocs をネットワークドライブ T: として割り当て、「サインイン時に再接続する」にチェック。
  3. 自動常駐の登録: フォルダ内の register_startup.bat をダブルクリックして実行。
